# EK-CORE 提权全流程（按内核对象与判据拆解）

本文件只描述"流程为什么这样走"，不记录某次补丁。所有结论都标注证据来源：
`K` = 内核镜像自带字符串/反汇编；`L` = 设备日志行；`S` = 二进制符号/字符串。

---

## 0. 前提：tracefs 能不能给我们"页归属"证据

EK-CORE 的利用是 **UAF + 零写**，写之前必须确认"受害者那个 slab 页已经回到 buddy 并且被我们的喷雾拿回来了"。
确认这件事只能用 kmem tracepoint 的记录，按可靠性排序：

| 事件 | 提供什么 | 我们用它做什么 |
|---|---|---|
| `kmem_cache_alloc` / `_node` | `call_site, ptr, bytes_req, bytes_alloc` | 找 cred / task_struct 的地址（Stage 3）、算 KASLR（`call_site` 严格一致） |
| `mm_page_alloc` | `page, pfn, order, migratetype, gfp_flags` | **页归属证据**：pfn 等于受害者 slab 的 pfn 且 order≤1 → 页回来了 |
| `mm_page_free` | `page, pfn, order` | 同一件事的反向证据 |
| `mm_page_pcpu_drain` / `_batched` / `_zone_locked` | 同上变体 | 兜底：不同内核把页走哪条路径 |

前提链条（缺一不可）：
1. `events/kmem/*/enable` 或 `events/kmem/rss_stat/trigger` 里写 `enable_event:kmem:<name>` 能被系统接受；
2. 真的产生记录（`trace` 或 `trace_pipe_raw` 里能看到该事件的 id 与正文）；
3. 记录的正文布局要知道（`format` 的 `offset:N`，读不到就按内核镜像里的 `trace_event` 格式串推断）。

**证据**
- `K` `honor_kernel_Image`(6.6.118) `0x222b79b` = `"page=%p pfn=0x%lx order=%d migratetype=%d gfp_flags=%s"`
  → 页记录布局 `page@0 pfn@8 order@16 migratetype@20 gfp@24`，且因为带 `gfp_flags` 字符串，正文常超 112 字节 → 内核改用**扩展记录头**（`type_len==0`，`total = 4 + u32(o+4)`，正文从记录头 **+8** 开始）。
  - 注意别把 `type_len==29` 当扩展：29 是 `commit`/padding 记录（正文长度字段被复用为时间增量），`parse_events` 里 `if(!time_delta) break;` 必须跳过，否则会把提交记录当事件解码，pfn/pid 全是垃圾。
- `L` `dev900.log`：`[trace] enable ok=1 fail=5` + `[base] order1_pages=7` + `plant1 slab_pfn=0x9a9fb0 half=1 slab_own=31/31` → 那台机上**至少一个页事件真的产生了记录**。
- `L` `dev910.log` / `(5).txt`（同 6.6.118，PPG-AN00）：`[trace] holder /events/kmem/rss_stat armed=8/8`，但 `[raw]` 里从头到尾只有 `id=269`（cache_alloc），`order1_pages=0` → 页事件**没有产生记录**，即使日志说 armed。

结论：`armed=N/N` 只证明"写入 trigger 返回 0 或 EEXIST"，**不证明事件在工作**。判断标准只能是"记录里出现了该事件的 id"。

## 1. Stage 1：KASLR slide

两条路，任一成立即可：

- **页配对**：同一 pfn 同时出现在 `mm_page_alloc(order=1)` 与 `timer_create` 的时序里，用 pfn 差推出 `_text` 的 2 MiB 对齐基址。
  需要页记录 → 页事件不可用时不可用（`L dev900` 就是这条路：`candidates=22 best=0xffffff7f80000000 votes=195`）。
- **call_site 严格一致**：`kmem_cache_alloc` 记录里的 `call_site` 必须与被 hook 的 `bl kmem_cache_alloc` 目标严格相等（KCFI 下允许 `[addr-0x80, addr]` 的 thunk），差值即 slide。
  只需要 cache_alloc 记录 → **页事件被拒时仍然可用**（`L (5).txt`：`via call_site samples=512 base=0xffffff8000000000 (all samples agree)`）。

所以 slide 不是这台机的瓶颈。

---

## 2. Stage 2：UAF 窗口（唯一真正的瓶颈）

流程：
1. 起受害者进程，`timer_create(CLOCK_THREAD_CPUTIME_ID)` 若干，其中一个（VICTIM_IDX）设为"休眠"状态；
2. 让 `k_itimer` 分配落在目标 slab 的一条链上，记录 `V`（`k_itimer*`）与 `slab_pfn = V>>12`；
3. **把同 slab 的其它对象全部释放**（`slab_own=31/31` 表示 32 个对象里我们占了 31 个），再把页清空 → 页回到 buddy；
4. 这时再喷射，让我们的对象占回同一页；确认这点的唯一手段是页事件里出现 `pfn == slab_pfn`；
5. 确认后**才**允许写。因为写操作本质是"操作一条红黑树的节点"，写在没有归还的页上 = 踩别人的树 → 内核断言/空指针 → panic。

`MODE_ZERO` 的写法（`S` 反汇编 + `L` 行为）：
- 把 `target` 当作 `rb_node`，清 `__rb_parent_color`；
- `rb_erase` 时 `if (!tmp) __rb_change_child(parent, NULL, old, root)`，于是把 **0 写进 `parent->rb_left` 或 `rb_right`**；
- 目标 `target` 必须落在那条 rb 链上（`task->cred` 或 `cred->uid` 附近的 tile），否则写的地址完全不对。

因此 Stage 2 的判据必须满足三件事同时为真：
`event == mm_page_alloc`、`pfn == slab_pfn`、`order <= 1`；
可选加强：`pid == 我们的喷雾 tid`、`slab_own >= 28`。

---

## 3. Stage 3：cred / task_struct 泄漏

- `kmem_cache_alloc` 记录里 `bytes_req/bytes_alloc` 等于 `cred`、`task_struct` 的 size class（SLUB 按 class 上取整，`0xA8→0xB0/0xC0`、`0x1340→0x1400`，这是 9.91 之前全部失败的根因：`rq == al` 严格相等会把这些记录判成 free）。
- cred 的 `site_low` 必须等于 `prepare_creds` 里 `bl kmem_cache_alloc` 的低 21 位；`copy_process` 同理给 `task_struct`。
- 5.10 的字段偏移与 6.x 不同（`req@16 alloc@20` vs `req@16 alloc@24`），嗅探必须允许两者。

---

## 4. Stage 4/5：构造 fake cred 并写进去

两条现实路线：

**A. fake cred（我们当前实现）**
1. 在用户态准备一块与 `struct cred` 同布局的 blob：8 个 id 全 0、caps `cap_effective/permitted/inheritable/bounding/ambient` 全 `0x1ffffffffff`、`security/user/user_ns/ucounts/groups` 指向真实对象的地址；
2. 让这块 blob 落在我们控制的内核 slab 页上；
3. 用 `MODE_ZERO` 的 rb_erase 把 `task->cred` 指向它（`OFF_TASK_CRED`），再写一次把 `task->real_cred` 指过去（`OFF_TASK_CRED - 8`）；
4. 子进程醒来后 `setresuid(0,0,0)`，读回 `/proc/<pid>/status` 的 `Uid:` 与 `Gid:` 四段是否为 0。

关键点：**8 个 id 必须连续写、起点是 `CRED_UID_OFF/4`**（uid@4 的内核上 `suid/sgid/euid/egid/fsuid/fsgid` 全在后面的 u32 里）；写 `cred` 与读 `real_cred` 是两件事，必须都改。

**B. 原地改真实 cred（gaaa/HAPT 的做法）**
`S` 字符串：`[cred] attempt %d/12`、`[real_cred] pass %d/4 -> uid=%u r=%u`、`[real_cred] child r=%u still nonzero; UAF fallback`、`task->real_cred installed (uid: 0)`、`CRED_LEAK_METHOD=perf_event_open_kmem_cache_alloc+capset`。
即：不伪造 cred，直接对**泄漏到的真实 cred** 做 4 趟 pass，每趟独立 UAF、每趟读回，失败就换一次新 UAF；caps 用 `capset()` 而不是伪造。

---

## 5. Stage 6/7/8：SELinux、子进程、KernelSU

- SELinux：把 `selinux_state.enforcing` 写成 0（同一套零写，目标是 `selinux_state + 0x11` 这个字节）；证据是 `getenforce → Permissive`。
  这一写同样是"写别人的树"，所以**也必须先有窗口证据**，否则就是 5.10/6.1 那几次 panic 的真正原因。
- 子进程：父进程把 cred 改好后唤醒子进程，子进程 `setresuid(0,0,0)` 并回报 `uid=0 euid=0`；父进程必须 park（不能让 `k_itimer` 所在页被回收）。
- KernelSU：拿到 uid=0 后用管理器里的 `ksud` `late-load` 装 LKM；`--package-name` 只在加载那一刻生效。

## 6. 失败分类（对号入座，不要乱改判据）

| 现象 | 层 | 判定依据 |
|---|---|---|
| `order1_pages=0` 且 `[raw]` 只有 cache id | **挂事件** | 页事件没产生记录，属环境/权限，不是判据 |
| `enable ok=0` / 全 `errno=13` | 环境 | tracefs 被 SELinux 拒 |
| `hit=0` 但页记录有、pfn 不等 | 窗口 | 页还没回到我们手里，继续等/换喷雾 |
| `cred/task` 匹配为 0 | 判据 | size class 上取整、`site_low` 严格一致 |
| 写了但 `su` 不可用 | 收尾 | id 只清了部分、`real_cred` 未装、caps 错位 |
| panic | 安全 | 无证据就写（zero 模式最危险） |

## 7. 6.6.118 这台机（PPG-AN00）到底卡在哪

- slide：OK（`call_site` 一致）。
- cred/task：OK（`[cred] hit# req=0xa8 alloc=0xc0`、`[task-scan] any-pid 兜底命中 req=0x1340`）。
- **窗口：拿不到页记录**。`armed=8/8` 是写入返回的假象，`[raw]` 里没有页事件 id，所以 `order1_pages=0`。
- 因此在"无证据不写"的闸下必然停在 `[~] 无页级窗口证据`。

结论一句话：**这台机上 EK-CORE 卡在"页事件不产生记录"，与 cred 写入、SELinux、KernelSU 全部无关**。

要往前推进只能先解决"页记录"，顺序：
1. 逐事件打印：路径、写入 errno、回读 `enable` 的内容、是否有记录（事件 census）；
2. 若直接 enable 全拒，验证 `rss_stat/trigger` 的 `enable_event:` 是否真的把子事件挂上（回读子事件 `enable` + 记录 census）；
3. 只有 census 里出现 `mm_page_alloc`/`mm_page_free` 的 id，才谈得上窗口判据。

这三步都是只读检查，不涉及写入，不会 panic，也不会再"改一版猜一版"。

## 8. 9.142 起的做法：先普查，再谈窗口

9.142 把上面三步做成了两个只读/平级证据，不再靠猜：

### 8.1 `census` 子命令（只写 tracefs，不碰内核内存）

```
su -c '/data/local/tmp/extract-kit/ek-core-uid0 census'
```

入口（9.143 起）：**只有 adb**。9.142 一度在设置里加过一行「只读普查（census）」，
9.143 按需求撤掉了那行（界面恢复原样）；`Modes.byId("census_EK-CORE")` 仍留在 `PayloadCatalog`
里，标 `persists=false`、成功标记 `CENSUS_DONE`，只供设备侧调用，界面点不到。
它只写 tracefs，不受 `device.cfg` 拦截；tracefs 门禁按原样（只有 `preflight_EK-CORE` 豁免），
所以真遇到 tracefs 不可写时它会自己把 `tracefs_writable=0` 打在 verdict 里。

每个候选事件一行：

```
[census] ev=%s dir=%d id=%u id_errno=%d en0='%s'(%d) wr=%d wr_errno=%d en1='%s'
```

- `dir`：1 = 走 `/sys/kernel/tracing`，2 = 走 `/sys/kernel/debug/tracing`，0 = 两处都读不到 id。
- `en0`/`en1`：写之前、写之后的 `enable` **回读内容**（不是写入返回值）。
- `wr`/`wr_errno`：直接写 `<event>/enable` 的结果与 errno（`wr_errno` 在 `close` 之前取，避免 close 覆盖 EACCES/ENOENT）。

holder 通道（`rss_stat`、`sched_switch`）逐个 `enable_event:kmem:<ev>` 打 `trig=%d errno=%d`，再回读 holder 自己的 `enable`。

然后真开窗 300ms：清环 → `tracing_on=1` → `force_rss()` 自己造页事件 → 关窗 → `scan_event_ids()` → 逐核解析，按事件 id 计数：

```
[census] recs ev=%s id=%u n=%ld
[census] recs total=%ld unknown_id=%ld window_ms=300
[census] verdict page_events_usable=%d page_enable_any=%d cache_alloc_recs=%ld tracefs_writable=%d
```

判据（只有这一条算数）：

| `page_events_usable` | `page_enable_any` | `cache_alloc_recs` | 结论 |
|---|---|---|---|
| 1 | 任意 | 任意 | 页事件可用 → 回到 burst，窗口判据照旧 |
| 0 | 1 | >0 | enable 写得进去但页事件不产记录 → 只能走 `kmem_cache_alloc` 通道（9.142 的同页 alloc 证据） |
| 0 | 0 | 任意 | 连 `enable` 都写不进 → tracefs 被拒（SELinux/权限），先修环境 |

### 8.2 第二条窗口证据：`page-claimed-by-alloc`（hit=2）

页事件不可用时，不放弃、也不盲写。burst 里新增一档：如果 `kmem_cache_alloc` 记录的 `ptr` 落在 **同一个 slab 页**（`((ptr-base)>>12)&~1ULL == slab_pfn`）且 `pid` 是我们的喷雾线程，就认为这一页确实回到我们手里：

```
[+] plant%d page-claimed-by-alloc ptr=%#llx pfn=%#llx pid=%d
```

- `hit=1`：页事件直接命中（原判据）。
- `hit=2`：同页 alloc 命中（新证据）。
- `hit=0` 且 `foreign=1`：这页被别人拿走了，退避重试，**不写**。

硬闸文案（9.142 起）：

```
[~] plant%d 无页级窗口证据（hit=0：页事件与同页 alloc 都没命中），跳过写入以免 panic
```

里面那句固定子串「无页级窗口证据」被 UI 用来挂提示（`StageMap.hint`），改文案时保留它。

### 8.3 顺序建议

1. 先跑 `census`，看清 `page_events_usable`。
2. 若为 0 而 `cache_alloc_recs>0`，直接跑 `chain_EK-CORE`——同页 alloc 证据会接手，不必再等页事件。
3. 若 `tracefs_writable=0` 或全 `errno=13`，先解决 SELinux/权限，别改判据。

## 10. 分支 payload 语义（9.145 起）：6 支不是 6 份源码

9.144 及以前，`assets/payload/fam/ek-core-uid0-<fam>` 这 6 支只差一个
`-DEXPECT_FAMILY="<fam>."` 闸门串，偏移与符号地址全部来自同一份
`payload/src/device_config.h`（6.6.118-android15-8-…-4k）。也就是说：**换族只换了
「自我拒绝」的判据，没换任何真值**。更糟的是 `EXTRACTKIT_FAMILY_ID` 默认
`"generic"`，`build_fam.py` 又从不传它，于是 `fam_is_61()` 恒 0，6.1 的三处专用
策略（窗口闸门放宽、leak 重试、tries=12）一直是死分支。

9.145 改成「族默认层 + 标定闸门 + 运行期覆盖」三层：

1. **族默认层**：`payload/src/family_defaults.h`，编译期按
   `EXTRACTKIT_FAMILY_INT` 选默认。目前有真依据的族差异只有两条：
   - `cred->uid` 偏移：5.10 / 5.15 / 6.1 是 **0x4**（uid/gid 各 4 字节），
     6.6 / 6.12 / 6.18 是 **0x8**（uid_t 与 gid_t 之间多 4 字节填充）；
   - 5.10 没有 `cred->ucounts`，该槽位退回 `cred->groups`。
   其余偏移（task_struct.cred、k_itimer 内嵌、cred 各字段）按 6.6 布局兜底，
   并在 `index.txt` 里标 `uncalibrated`。
2. **标定闸门**：只有 6.6 一族有真镜像（PPG-AN00）标定过。非标定族把 8 个
   文本符号地址（`STATIC_TIMER_SITE` / `TIMER_SITE_LOW21` / `SELINUX_STATE_STATIC` /
   `PANIC_ON_WARN_STATIC` / `ROOT_USER_STATIC` / `INIT_USER_NS_STATIC` /
   `INIT_UCOUNTS_STATIC` / `INIT_GROUPS_STATIC`）**全部置 0**，让既有判据自动接管：
   - stage_write 看到 0 直接跳过；
   - `main` 的 offsets-only 判据（`STATIC_TIMER_SITE==0`）自动成立，不再做 slide
     计算 → 不会因为「拿 6.6 的地址去减别的内核」而 panic；
   - `MODE_FAKE` 在 `build_fake_cred()` 之前早退，日志
     `[-] plant<n> 拒绝 fake：cred 的 user/user_ns/groups 未标定（family=<fam>）`。
     这一步是硬需求：`0 + g_slide` 会把 `cred->user` 指到随机内核地址，一碰就崩。
3. **运行期覆盖**（优先级从高到低）：`device.cfg`（标定档案，含符号地址）>
   `/sys/kernel/btf/vmlinux`（`--btf`，只解决结构偏移）> 族默认层 > 编译期 6.6 真值。

启动日志会明说当前是哪一层在生效：

```
[payload] family=6.1 calibrated=0
[cfg] family defaults (uncalibrated; supply device.cfg or rely on BTF)
```

### 10.1 选哪一支、开关在哪

| 情况 | 用的资产 |
|---|---|
| release 命中矩阵（5.10/5.15/6.1/6.6/6.12/6.18） | 对应 fam 分支版（9.145 起默认，不再需要开关） |
| 矩阵外（如 6.7）或解析不出 | 字面版 `payload/ek-core-uid0`（= 6.6 标定），日志标「不在分支矩阵内」 |
| `/data/local/tmp/extract-kit/use_literal` 存在 | 强制字面版（对照实验 / 回滚用） |
| `/data/local/tmp/extract-kit/use_fam` 存在 | 强制分支版（旧开关，仍认；`use_literal` 优先） |

跨族仍会被 `EXPECT_FAMILY` 拦住（返回 3），所以「装错一支」不会静默乱跑。

### 10.2 一致性由脚本钉住

- `tools/build_fam.py`：编 6 支时传 `-DEXTRACTKIT_FAMILY_ID="<fam>"` 与
  `-DEXTRACTKIT_FAMILY_INT=<major*100+minor>`，编完断言族身份串真进了二进制，
  再写 `assets/payload/fam/index.txt`（`<fam> <sha256> <family_int> calibrated|uncalibrated`）。
- `tools/check-fam.py`：6 支存在、sha 互异、每支只含自己的族身份串（按 NUL 包住的
  独立 token 判，裸 substring 会被 `ksu_stage.h` 里的 KMI 映射表骗）、
  `index.txt` / `SHA256SUMS.txt` / `PayloadCatalog.PER_FAMILY` 三方一致、
  未标定支不得带 6.6 的地址串、6.1 与 6.6 不得编出同一份。
- `FamilyDefaultsTest`：把上面这些约定写成单测（5.x/6.1 的 0x4、5.10 的 ucounts
  回退、`FAMILY_IS_61 == FAMILY_IS_601`、非标定族置 0 清单、index.txt 与 catalog 对齐）。

## 12. 9.147：让「窗口」这件事第一次有可观测面

9.146 之前，真机上 plant2/plant3 的现象是 `recs=0` 然后直接 `[~] 无页级窗口证据`。
9.147 不改判据，只改两件会让人误判的东西：**事件到底开没开**，和**窗口里到底发生了什么**。

### 12.1 enable_event 的规则是永久的（这是 recs=0 的根因）

`arm_kmem_events()`（原 `enable_events()`，`payload/src/ek-core-uid0.c:426`）用一个
enable_event 触发器挂 `kmem:kmem_cache_alloc` 与 `kmem:mm_page_alloc`，拿到 EEXIST 就当作
「已经挂好」。但触发器规则只要写一次就一直存在，而旧版 `trace_stop()` 收尾会写
`.../enable = 0` —— 事件被关掉、触发器还在。下一轮重挂只拿到 EEXIST、事件却始终关着，
于是整个窗口一条记录都没有。现在：

- `trace_stop()`（:590）只关 `rss_stat` / `sched_switch` 与 `tracing_on`，**不碰 kmem enable**；
- 每次重挂都重新数一遍命中的事件（`g_page_armed = 0` 先清再数），不再相信 EEXIST；
- `trace_start()`（:569）在 `tracing_on=1` 之后回读三个文件，打一行

  ```
  [arm] start page_enable='1' cache_enable='1' tracing_on='1' armed=2
  ```

  这一行是「事件真开着」的唯一证据。界面把它归到「开启 tracefs 事件」阶段（`StageMap.TRACE`）。

### 12.2 `[win]`：每轮窗口的分类计数

窗口内读到的记录按事件类型分桶，窗口 900ms → 1500ms：

```
[win] plant2 recs=14 cpus=1 ca=9 cf=5 pa=0 pf=0 unk=0 same_page=0 same_mine=0 dmin=1f armed=2
```

| 字段 | 含义 | 怎么读 |
|---|---|---|
| `ca/cf` | `kmem_cache_alloc` / `kmem_cache_free` | 有 ca 没 cf → 喷雾把 slab 拿满了 |
| `pa/pf` | `mm_page_alloc` / `mm_page_free`+`pcpu_drain` | pa=0 且 armed=2 → 页事件根本没进缓冲 |
| `same_page` | 同页 alloc（`(ptr-base)>>12` 落在受害者 pfn） | 这是 9.142 加的平级窗口证据 |
| `same_mine` | 同页且 pid 是我们的喷雾线程 | 只有它=1 才算真窗口 |
| `dmin` | order≤1 的 page_alloc 离目标 pfn 的最近距离 | 一直很大 → 喷雾没落在同一 zone/迁移类型 |

判据没变：**`same_mine`（或 hit）才是窗口**，其余都只是诊断。

### 12.3 `[pipe]` 兜底：动手，但不算证据

`pipe_plant()`（:2965 起）原来被 `if (0 && …)` 关死，等于兜底从来没存在过。现在放在
「放弃闸口」之前执行，条件是 `!hit && !foreign && mode == MODE_FAKE && g_pipe_fallback`：

```
[pipe] wrote=4096 off=0x1200 page=1 hit=0（未验证，交给 uid 校验）
```

- 撑到 `PIPE_PLANT_MAX`(64) 根 pipe，2 页/根，LIFO 抢 per-cpu 页；
- fd **故意不 close**：关掉页就还回 buddy，若那页正是受害者页，等于把 fake cred 交出去；
- 写成功**不置 hit**（那页是我们自己的匿名页，不构成"内核把受害者页还给我们"的证据），
  只置局部 `pipe_wrote` 让放弃闸口（`if (!hit && !pipe_wrote)`）放行；
- `--no-pipe` 关掉兜底，只走 tracepoint 判据。

### 12.4 `[tile]` 也还留着

零写阶段（`MODE_ZERO`，selinux_state / panic_on_warn）依旧必须先有窗口证据才动手：
盲写等于在别人的红黑树上拆链。所以 pipe 兜底只对 `MODE_FAKE` 开。

## 13. 9.148：把"没认领到"这件事拆开看

### 13.1 9.147 的诊断放错了层（run#1 的直接教训）

`run#1 触发（busy=(11).txt`（PPG-AN00 / 6.6.118 / 9.147 / 6.6 族）里，
`[win]` 一次都没出现，而 plant 三次都只打了一行：

```
[+] plant1 target=64xx etid=64xx code=2 status=9
[-] plant1 victim not captured (recs=0); retryable
```

原因不是 `[win]` 被过滤，也不是字符串没编进二进制（6.6 族 payload 里
`[win]`×1 `[pipe]`×2 `[arm]`×1 都在），而是**根本走不到**：

- `run_plant()` 的顺序是 harvest → 按 `pid==etid && req==alloc==TIMER_OBJ`
  过滤 → 命中 `VICTIM_IDX` 那条才拿到 `V` → 之后才 `mark_stage("burst")`
  进 1500ms 窗口、才打 `[win]`；
- victim 认不出来就直接 `res->retry=1` 返回，窗口循环一次都没跑。

所以 9.147 的窗口诊断是"事后证据"，对"事前认领失败"完全无效。
真正缺的是**认领失败本身的分层信息**：是窗口里没有记录？有记录但 pid 不对？
pid 对了但尺寸不对？

### 13.2 三档认领（`plant_claim_scan`）

```
for (pass = 0; pass < 3; pass++) {
        if (pass == 1) usleep(20000);          /* 让 reaper 把记录刷完 */
        cnt = harvest(g_evs, 400000);
        ...
        plant_claim_scan(pass, etid, T, cnt, &nrec, &V, &site0);
        logf("[claim] plant%d pass%d cnt=%d nrec=%d V=%#llx\n", ...);
        if (V && site0) break;
}
```

| 档 | pid 条件 | 尺寸条件 |
|---|---|---|
| pass0 | `pid == etid` | `req == TIMER_OBJ && alloc == TIMER_OBJ` |
| pass1 | `pid == etid` | 只要求 `req == TIMER_OBJ`（alloc 允许 `req..req+0x80` 的对齐膨胀） |
| pass2 | `pid == etid \|\| pid == 目标进程 tgid` | 同 pass1 |

- pass1 的存在理由：`kmem_cache_alloc` 的 `bytes_alloc` 未必等于 `bytes_req`，
  一旦 slab 里那格是别的 cache 尺寸，严格档会整批丢掉；
- pass2 的存在理由：`timer_create` 由 `exec_thread` 发起，但记录里的 `pid`
  是**调度到写记录时的当前任务**，极端情况下会落到同 tgid 的别的线程上；
- 三档都只放宽"匹配"，**不放宽索引**：仍然要求 `nrec > VICTIM_IDX`，
  否则写进去的是活 timer 的 node，等于自己炸自己；
- 认领成功但 pass>0 会单独打一行
  `[!] plant%d 第%d档才认领到受害者（严格档未命中）` —— 这一行出现就意味着
  尺寸/pid 判据和内核实际行为有偏差，下次该改的是判据而不是窗口。

### 13.3 三档全空时把窗口倒出来（`plant_diag`）

只打一种诊断是不够的，因为 `recs=0` 有三种完全不同的成因，修法也完全不同：

```
[diag] plant1 cnt=7386 etid=6512 alloc=120 free=7100 page=166 site_hit=0 timer_sz=0
[diag] plant1 alloc sizes: 0x108/0x108 x2049 0x40/0x40 x310 0x1000/0x1000 x8
[diag] plant1 alloc pids: 6512 x0 6513 x120 6401 x33
[diag] plant1 probe self_thread=6602 pn=41 pid_hit=8 size_hit=8
```

- 第一行给四个总数：`alloc`/`free`/`page` 分别是三类事件的条数，
  `site_hit` 是 call_site 低 21 位命中的条数，`timer_sz` 是尺寸命中条数；
- 第二行是 `bytes_req/bytes_alloc` 的 top6，用来回答"记录里到底有没有 0x108 这个尺寸"；
- 第三行是 alloc 的 pid top6，用来回答"记录里的 pid 到底是谁"（`x0` 就是该 pid 一条都没有）；
- 最后还会**自己起一个 probe 线程**：主进程内 `timer_create` 8 次，
  取自己的 tid，harvest 之后看能不能在记录里认出自己（`pid_hit`/`size_hit`）。
  这一步把"没有页事件"和"有记录但认不出"彻底分开：
  - `pa=0` 且 probe `pn=0` → tracefs 里根本没有 kmem 记录（SELinux/权限/事件没开）；
  - `pn>0` 但 `pid_hit=0` → 记录里的 pid 语义和我们以为的不一样；
  - `pid_hit>0` 但 `size_hit=0` → 尺寸判据错（这时该动的是 `TIMER_OBJ`）。

## 14. 9.149：plant 之后日志为什么直接断掉

run#1（busy=12，9.148 真机，PPG-AN00 / 6.6.118 / 分支 6.6）这一轮的日志停在：

```
[+] plant1 slab padding=4650
[ids] alloc=0 free=0 pa=0 pf=0 pfb=0 drain=0（...）
[arm] start page_enable='?' cache_enable='?' tracing_on='1' armed=6
```

之后一行都没有：既没有 `[claim]`（9.148 的三档认领一次都没打印），也没有
`[+] plant1 target=...`（wait_zombie 都没走到）。这跟 busy=11 那一轮完全不同 ——
那一轮至少走完了 3 次 plant 并打出 `victim not captured (recs=0); retryable`。
也就是说 **9.148 的三档认领代码根本没有被执行过**，问题在它之前的"等受害者报到"。

### 14.1 那条阻塞 read 是黑盒

`run_plant()` fork 出受害者之后，父进程要等孩子在 `exec_thread` 里写出 `'R'`
才算"受害者已就位"（之后才 trace_start、再 ack 让孩子建 timer、execve）。
原来的代码是一次**阻塞**的 `read(ready_p[0], &ch, 1)`。孩子只要在写 'R' 之前
死掉或卡住，父进程就永远停在这一行：不打印、不超时、走不到 `wait_zombie()`
的 4 秒超时，连 `trace_stop()` 都不做。日志停在上一行，看起来像"日志被截断"，
实际是**父进程被自己阻塞住了**。

### 14.2 `logf()` 的写序是第二个嫌疑

`logf()` 原来是先 `vprintf(stdout)` 再写落盘文件 `/data/local/tmp/ek-core.log`。
stdout 的对端是 App 那一侧的管道读端：界面被杀、被 freeze、或者读得比写得慢，
管道写满时 printf 就会**阻塞在写操作里**，那一行既进不了落盘文件、也不再往下走。
于是"adb 日志"和"落盘副本"会同时停在同一个位置，把真正卡住的点掩盖掉。

### 14.3 三处改动

1. **先落盘再 stdout**：`logf()` 改成先 `write()+fsync()` 落盘，再尽力写 stdout；
   main 里对 fd 1 设 `O_NONBLOCK`（失败则 `g_stdout_live=0` 不再尝试），
   并 `signal(SIGPIPE, SIG_IGN)` —— 读端先死时 payload 不能跟着静默消失。
2. **阶段回报**：新增 `stage(char)`，受害进程每走完一步往 ready 管道写一个字母：

   | 字母 | 地点 | 含义 |
   | --- | --- | --- |
   | `T` | `run_target` 开头 | 拿到 tgid，开始建碎片内存 |
   | `A` | `prepare_fragmented_range()` 之后 | VMA_COUNT 页的 VMA 铺好 |
   | `B` | LOCKERS 循环之后 | mprotect 抖动线程起齐 |
   | `C` | `killer_fn` 之后 | 杀线程就位 |
   | `D` | `pthread_create(exec_thread)` 之后 | 建 timer 的线程起来了 |
   | `R` | `exec_thread` 收到 ack 后 | 受害者就位（原来唯一的信号） |

3. **父进程心跳**：那次阻塞 read 换成 `poll()` 200 ms 一轮、总超时 15 s 的循环：

   ```
   [hb] plant1 stage=A at 12ms
   [hb] plant1 wait stage=D pid=10674 state=S 2000ms
   [hb] plant1 stall stage=D pid=10674 state=D after 15000ms
   [-]  plant1 trigger never ready (stage=D state=D 15000ms)
   ```

   卡住时一并打 `/proc/<pid>/stat` 的状态字母：`D`=不可中断睡眠（多半卡在内核里，
   例如 `mmap_read_lock_killable`）、`S`=在睡眠等锁、`Z`=已死但父进程还没收、
   `?`=进程已不存在。超时后 kill + waitpid + `trace_stop()` 再退出，不再把设备
   留在"按住半成品"的状态里。

## 17. 9.152：reclaim 链对 zero 阶段同样生效

### 17.1 busy=(15) 现场（9.151 真机，PPG-AN00 / 6.6.118 / SELinux Enforcing）

这一版**整条链第一次走通了 fake 与 real_cred 两个阶段**：

- 预检干净通过：`[base] recs=17153`、`[base] via call_site samples=512 base=0xffffff8000000000 (all samples agree)`、
  `[check] READY` → App 打印「✓ 预检通过（[check] READY）」。
- 主链 `fake`：`[cred] exact-size hit preferred: 0xffffff8812ba9f00`、
  `[cred] site-hit 0x38458: total=11 childPid=1`、
  `[+] child=14129 cred=0xffffff8812ba9f00 target=0xffffff8812ba9f08`。
- plant1 三连：`[claim] plant1 pass0 cnt=400000 nrec=4096 V=0xffffff892b5bcc60`、
  `slab_pfn=0x92b5bc half=0 recs=4096 slab_own=31/31 slide=0x1880600000`、
  `[uaf] stream miss; trying pipe reclaim fallback (wrote=0 off=0xcd8)` →
  `[pipe] wrote=64 reclaim=1 off=0xcd8 (stream miss)` → `[+] plant1 reaped status=0x9`。
- `[+] task->real_cred installed A=0xffffff89bf9ddc50`、
  `[+] fake cred A=0xffffff892b5bccd8 selinux_state=0xffffffd9029ba418`。

**唯一的新卡点**：selinux 零写阶段
`[+] stage selinux target=0xffffffd9029ba411 mode=zero attempt=1/1` 之后

```
[+] plant1 burst hit=0 foreign=0 free_seen=0
[~] plant1 无页级窗口证据（hit=0），跳过写入以免 panic
[~] stage selinux 重试（窗口未命中，换新 victim）
[-] stage selinux exhausted retries (1)
```

然后 `[ksu] panic_on_warn=-1` → `CHAIN_STOP:panic_on_warn_set`，驻留收摊。

### 17.2 根因

9.151 的回收链条件写的是 `if (!hit && !foreign && mode == MODE_FAKE)`：

- fake 阶段进得去 → pipe `wrote=64` → `hit=1` → 闸口放行 → 写入成功；
- zero 阶段被 `mode == MODE_FAKE` **挡在回收链外面** → `hit` 保持 0 →
  撞上 `if (mode != MODE_FAKE && !hit && !foreign && !free_seen)` 的放弃闸 →
  `res->retry = 1` → 重试一次后 `exhausted retries`。

即：同一台机、同一条 pipe 通道、同一页，fake 拿得到，zero 因为一个多余的
模式条件根本没去拿。零写阶段需要的正是「受害者页被我们重新拿到」，
和 fake 没有任何区别。

### 17.3 改动（一处条件）

```c
/* 9.152：三级 reclaim 对所有模式开（fake / zero 都要）。 */
if (!hit && !foreign) {
        ... pipe_plant() -> hit=1 ; aio_plant() -> hit=1 ...
}
```

- `mode == MODE_FAKE` 从条件里删掉，fake/zero 走同一条 stream → pipe → AIO 三级链。
- 放弃闸保留，但语义变成「回收链全灭（pipe 与 AIO 都没拿回页）才放弃」，
  这正是它原本要防的情况（在别人的红黑树上拆链）。
- 零写阶段的判定不再靠 tracepoint 存在与否，而是靠 pipe/AIO 是否真的拿到页。

### 17.4 为什么这样就够

9.104 时代 zero 阶段本来就走这条兜底（tracepoint 被 SELinux 关死的机器上
它没有别的通道），9.151 把兜底加回来时顺手用 `mode == MODE_FAKE` 限死了范围，
才是这次失败的唯一原因。这一版只回退那个多余的限制，不加诊断、不改判定。

## 18. 9.153：内核 .data 零写默认关闭（panic 的真因）

### 18.1 现象

9.152 装上真机后一跑就 panic / 重启。同一台机、同一条 pipe 通道，
9.151 只打了一行 `[~] plant1 无页级窗口证据（hit=0），跳过写入以免 panic`，
9.152 放宽 reclaim 条件后 selinux 零写**真的落盘了**，于是内核死。

### 18.2 机理：MODE_ZERO 会在 CPU 的 hrtimer 树里留下一个指向内核 .data 的坏 root

`build_payload()`（payload/src/ek-core-uid0.c:2815）对 MODE_ZERO 做的只有两件事：

1. 把目标地址 `S` 处的 8 字节清 0；
2. 把自己页里那个 `rb_node` 的 `rb_left` 指向 `S`（:2823 `*(uint64_t *)(buf + page_off + 0x10) = s_addr;`），
   随后 `rb_erase` 把该 CPU 的 `hrtimer_cpu_base` 的 `active.rb_root.rb_node` 改成 `S`。

rb_node 布局是 `__rb_parent_color@0 / rb_right@8 / rb_left@16`。
所以树根变成 `S` 以后，**下一次这个 CPU 插入任何 hrtimer，会先读 `S+8` 当 `rb_right`**。

- selinux 阶段：`S = SELINUX_STATE_STATIC + slide - 7`，`S+8 = selinux_state+1` ——
  这是内核 .data 里的一段非零字节，被当指针解引用 → 立刻 panic。
- fake_uid 阶段（:5134，写 `fc.A + 0x08`）：`S = A+8`，`S+8 = A+16` 落在
  **我们自己 socket 页里**（build_fake_cred 已把 `rb_left` 指回 S，且该页整页是我们的），
  所以那条零写是安全的，9.151 一直这么做也没事。

结论：`selinux_state.enforcing` 与 `panic_on_warn` 这类**内核 .data 地址**的裸零写，
在 6.6 上是结构性不可用 —— 不是概率问题，是下一次 hrtimer 一定踩。

### 18.3 崩溃后仍然卡在 panic_on_warn 的另一半原因

`payload/src/device_config.h:60`：

```c
#define PANIC_ON_WARN_STATIC 0xffffffc08216ae0cULL
```

`0x…0c` 只 4 字节对齐，而老代码要求 `(addr & 7) == 0` 才写，
于是 9.151/9.152 里 `[ksu] panic_on_warn=-1`（本机 /proc/sys/kernel/panic_on_warn
读不到）之后不是去写，而是直接 `park_forever("CHAIN_STOP:panic_on_warn_set")`。
两条路（写崩、或者不写而驻留）都走不通。

### 18.4 改动

1. 新增开关 `static int g_opt_permissive;`（紧跟 `g_pipe_fallback`），
   `opt_strip()` 认 `--permissive`；默认 **0 = 不写内核 .data**。
2. main 的 selinux 零写整段挂在 `if (!g_opt_permissive)` 之下：
   默认只打一行
   `[permissive] 跳过 selinux/panic_on_warn 零写（裸零写会让该 CPU 的 hrtimer root 指向内核 .data，下次插入即 panic）；SELinux 走 fake cred 的 kernel sid`，
   SELinux 域由 fake cred 里的 `SELINUX_SID_KERNEL`（build_fake_cred 已写 +0/+4 两处）负责。
3. panic_on_warn 块改成 `if (g_opt_permissive && read_panic_on_warn() != 0)`，
   对齐判定由 `& 7` 放宽到 `& 3`（`0x…0c` 现在合法），写入地址改为 `PANIC_ON_WARN_STATIC + g_slide - 7`
   （8 字节零写只覆盖那一个字节），两条 `park_forever` 全部换成 `logf` 后继续：
   `[ksu] panic_on_warn 地址不可用，跳过清零继续` / `[ksu] panic_on_warn 清零未命中，继续` / `[ksu] panic_on_warn 已清零`。
4. 老路仍可用：`--permissive` 时行为与 9.152 完全一致（想复现 panic 就带这个参数）。

### 20.3 关于「去掉 kmem 事件」—— 不能去

`/sys/kernel/tracing/events/kmem/` 下的两类事件用途完全不同：

## 21. 9.156 删预检导致稳定 panic，9.157 把 check 以非阻塞预热形式加回

### 21.1 用户数据

- 用户原话：「9.155 稳定成功、9.156 稳定失败」。同一台机器、同一份 payload（两版 assets 与 9.104 逐字节相同，`same 10 / diff 0`），只差 App 侧有没有先跑一次 `check`。
- 所以这不是概率问题，`check` 有必然存在的副作用。

### 21.2 副作用是什么

busy=(16)（9.155 的成功日志）主链第一屏就有：`[trace] /events/kmem/rss_stat: kmem_cache_alloc already armed`。

「already armed」说明 event 的 `enable` 状态是**跨进程保留**的：上一轮 `check` 进程已经替主链把能挂的事件挂上了。本机 SELinux 把 8 个 direct enable 全拒（`errno=13`），冷启动挂不上，9.156 的主链就带着更少的 armed 事件往下走，plant 之后 `hit=0`，pipe 回收落在没有被验证过的页上，8 字节零写打到别人的 rb_node → panic。

### 21.3 9.157 的改法（只改 App，payload 不动）

`ExtractEngine.kt` 主链之前插一段非阻塞预热：选中的 payload 是 `ek-core-uid0*` 时（链在 6.6 上会选分支 payload，所以用 `name.startsWith` 而不是 `== Payloads.UID0`），先跑一次 `check`（markers = `[check] READY`、timeoutSec 150、persistOnSuccess false）。

结果只写日志（`· 预热完成` / `· 预热未 READY`），**从不 return / 从不中止**。9.155 的行为（先 check 再主链）回来了，但没有恢复 `selfCheckArgs` 机制，也没有恢复用不存在参数 `--preflight` 的 `preflight_EK-CORE` 这个 mode。
